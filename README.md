# Minecraft Parcel (prototype)

A NeoForge 26.2 project plus a small self-hosted delivery API. The intended workflow is to use the vanilla Minecraft 26.2 Friends List as the recipient directory, then route parcels through the API so the recipient can collect them later from another single-player world.

## Current status

This is an initial project scaffold, not a finished or tested playable mod. The API implements authenticated inbox, send, and claim endpoints. The NeoForge module has its entry point, API transport, and an isolated bridge to the vanilla `PlayerSocialManager#getFriends()` API. The in-game screen, profile UUID extraction from the mapped friend data, safe ItemStack serialization/deserialization, and full end-to-end testing remain to be implemented.

Mojang's 26.2 Friends List is used only for friend discovery and identity. The mod does not depend on Mojang's withdrawn peer-to-peer play service. The 26.2 vanilla API documents `PlayerSocialManager#getFriends()`; exact profile-data access must be checked against the generated NeoForge 26.2 sources before wiring the UI.

## Requirements

Minecraft Java 26.2, NeoForge 26.2, JDK 25, and Gradle (or the Gradle wrapper generated by the NeoForge MDK).

## Build the mod

Open `mod/` in IntelliJ IDEA with JDK 25 selected, then run `gradle build`. The resulting jar is written to `mod/build/libs/`.

The current execution environment used to prepare this scaffold only has JDK 21, so the mod has not been compiled here. Use the official NeoForge 26.2 MDK if you want to regenerate the wrapper and refresh the Gradle workspace.

## Run the delivery API

From `backend/`, create a token per player. Configure `PARCEL_TOKENS` as comma-separated `minecraft-profile-uuid:long-random-token` pairs. For example:

```sh
PARCEL_TOKENS='11111111-1111-1111-1111-111111111111:replace-with-secret,22222222-2222-2222-2222-222222222222:another-secret' npm start
```

The API listens on port 8787 by default. Put it behind HTTPS before exposing it to the internet. `parcels.json` contains pending parcel payloads; back it up and restrict filesystem access.

## API

`POST /v1/deliveries` creates a parcel. JSON body: `{ "recipientUuid": "...", "items": [{ "stack": "serialized ItemStack data" }] }`.

`GET /v1/inbox` lists pending parcels for the authenticated profile.

`POST /v1/deliveries/{id}/claim` claims a parcel and returns its item payload. A production client must only remove items from the sender after the server has durably accepted the parcel, and must only insert received stacks after the claim succeeds. It also needs an idempotent receipt/acknowledgement protocol to protect against crashes between claim and inventory insertion; this prototype endpoint is intentionally not yet safe for real item-value transfers.

## Security and implementation notes

Do not trust a UUID supplied by the client as proof of identity. The example backend maps bearer tokens to UUIDs, but token provisioning and secure account binding still need to be built. Do not publish a server without TLS, rate limits, payload validation, and persistent database backups. The item payload must be encoded using Minecraft's registry-aware ItemStack codec, not a display name or item ID alone, so data components, enchantments, names, and durability survive.


## Version 0.2.0 — client UI milestone

The client UI can be opened with **P** (configurable under Options → Controls → Miscellaneous) or with the **Parcel** button beneath the player inventory. This version is an interface scaffold only: friend lookup, selecting item stacks, and live parcel delivery are not connected yet. See `BUILD_STATUS.md` for the implemented and outstanding work.
